Privacy Policy

GPH Intelligence MCP Server · Last updated: 2026-11-27 · Operated by CBEG Group LLC · Contact: cbeggroup@gmail.com

This policy describes how the GPH Intelligence MCP Server (https://gph-mcp-server.pages.dev/mcp) handles data. It covers the MCP service's data handling, not the contents of the underlying vendor directory.

What we collect

Each time one of our tools is called, we write a usage record containing the following.

  • The name of the tool, the time of the call, and the arguments sent exactly as they arrived, such as the service category, specialty, practice size, city, state, EHR system, budget range, search filters, a provider slug or an EHR product key. We copy the most useful of those arguments into columns of their own so we can count demand by category and place.
  • What came back: how many results there were, whether there were none, the identifiers of the providers shown, and the provider profile opened, if any. That is how we see which vendors practices actually look at.
  • A few labels we work out from the tool name and arguments, so we can read demand without rereading every record. They say how complete the request was (a signal score from 0 to 3 and a completeness figure from 0 to 100), which category and place it asked about, whether it looks like a practice's own question or a bulk read of the directory, which step of a search it was, and whether the answer came from our short-lived search cache.
  • The user-agent string the calling software sends, which names the program making the call. We keep it to see which programs send calls and how they behave.
  • The referring page, when the client sends one. We keep it to see which pages send people to the tools.
  • The country and network operator of the calling service, meaning its autonomous system number and the organization that runs that network. Our hosting provider, Cloudflare, derives them from the IP address. We record them for traffic measurement only, and they play no part in how a call is classified or answered.
  • Our own classification of the caller, made from the user-agent string and, for a browser client, the website the request came from. It records what kind of caller it is (an AI assistant, a developer tool or a crawler, for example), which assistant or agent it appears to be, what it seems to be doing, and whether it is one of our own test tools. We keep the labels and not the website address.
  • A session identifier, so calls made together can be read together. When the client sends back the MCP session id we issued at the start of the session, we store a shortened one-way hash of it, which links the calls in that session and nothing more. When it doesn't, we store a one-way hash of the IP address and user agent mixed with a value that changes every day, so those calls can only be linked within one day.
  • Whether the call was anonymous or used a legacy API key, and for a key, only its plan tier. We keep the tier to see demand by plan; the key itself is never stored.

When a caller goes over the rate limit, the first refused call in each window is written to our Cloudflare D1 log only. It does not go to Airtable. A legacy API key also has its call count and last-used time updated. For a pay-as-you-go key, we send a usage event with the key holder's billing customer id to Stripe, our payment processor. If that event fails, we keep the billing customer id in a retry queue for 7 days and then delete it. We receive your IP address from the network connection and use it only for rate limiting and as a passing input to the daily session hash above. Your raw IP address is never written to either store.

How we use it

To operate the service and return results; to enforce a request-rate safety valve (per-IP calls per minute, with a daily backstop); and to produce aggregate demand analytics on which categories, specialties, and locations practices ask about and how that demand arrives. Those analytics help us improve the directory and prioritize vendor coverage.

Storage and processors

Usage records are stored in Cloudflare D1, our hosting provider's own database. Airtable, our data processor, receives a copy for review, except for rate-limit refusal records and four fields (traffic class, cache status, vendor geography preference and service needs), which stay in D1 only. Neither store holds your IP address or an account identity. Your IP address is held only as part of the key for two rate-limit counters in Cloudflare KV: a per-minute counter, which expires automatically after 2 minutes, and a per-day counter, which expires automatically after 48 hours. The same counters are held briefly in the memory of the server instance handling your calls. Directory search results are cached for up to an hour so repeated searches come back faster, and that cache holds only the directory's answer, with nothing about who asked.

Retention

Individual usage records are retained for service-improvement analytics in Cloudflare D1 and Airtable for up to 24 months, after which they are deleted; aggregate, de-identified demand statistics derived from them may be kept indefinitely. Rate-limit counters expire automatically after 48 hours. Stripe retry entries for failed usage events are kept for 7 days and then deleted.

Sharing

We use Cloudflare as our hosting and infrastructure provider, including the D1 database, and Airtable as a processor. Stripe receives usage events only for pay-as-you-go API keys, so it can bill them. We use aggregate, non-identifying demand insights to inform vendor and sponsor outreach. We do not sell or share the query or demand data.

What we do not collect

No patient health information is requested or needed, because the tools take only service categories, specialties, places and similar filters about a practice, so please don't send patient data through this service. We don't store your IP address in usage records, set cookies, or require you to register. The session identifier links calls within one session or one day, and it is not a lasting user ID.
